# 寄信模式增益集：部署技術學習筆記

> 給非 IT 背景的人看的入門筆記。可以整份貼進 AI 對話，再照最後的「練習問題」一題一題問。

## 0. 一張圖看全貌

整個系統分三塊：

```
┌──────────────┐        ┌──────────────────────┐        ┌────────────────────────────┐
│ 同事的 Outlook │ ─────▶ │ 公司主機（範本服務）    │ ─────▶ │ 公司 Microsoft 365          │
│ Win/Mac/網頁版 │ HTTPS  │ Node.js + HTTPS 入口   │        │ Entra（登入）+ SharePoint   │
└──────────────┘        └──────────────────────┘        │ （存範本）                   │
        ▲                                               └────────────────────────────┘
        │ M365 管理中心把「增益集」分配給同事
```

一句話流程：同事在 Outlook 按「寄信模式」→ 打開公司主機上的網頁 → 用公司帳號登入 → 主機確認身分後，到 SharePoint 拿範本 → 同事填好插進目前草稿 → 自己按傳送。

## 1. Outlook 增益集是什麼

### 1.1 增益集 = 一張說明卡 + 一個網頁
- **XML（manifest，資訊清單）**：一張說明卡，告訴 Outlook「按鈕叫什麼、圖示長怎樣、按下去要開哪個網址」。它本身不含程式。
- **網頁（taskpane，工作窗格）**：真正的功能。按鈕按下去，Outlook 會在右側開一個小視窗顯示這個網頁。
- **Office.js**：微軟提供的 JavaScript 函式庫，讓網頁可以讀寫「目前正在寫的這封信」。

### 1.2 為什麼一定要有 HTTPS 主機
- 網頁一定要放在某個網址上，Outlook 才打得開。
- 微軟規定這個網址必須是 **HTTPS**，否則 Outlook 拒絕載入。
- 新版 Outlook、Mac、網頁版都是這樣，所以「只發一個檔案給大家安裝」行不通。

### 1.3 舊版（EXE）和新版（公司主機）的差別

| | 舊版 | 公司部署版 |
|---|---|---|
| 網頁放哪 | 每台電腦裝 EXE，在自己電腦跑一個 `localhost` 小伺服器 | 公司一台主機，大家連同一個網址 |
| 範本 | 每人自己存 | 集中存在 SharePoint，管理者發布 |
| 更新 | 每台重裝 | 主機更新一次，大家重開面板就是新版 |

### 1.4 怎麼發給大家
- **M365 管理中心 → 設定 → 整合式應用程式 → 上傳自訂增益集**，上傳 XML，指定給哪些人。
- 分配後，同事的 Outlook 可能要 **最多約 24 小時** 才會出現按鈕（微軟同步的時間）。
- 同事電腦 **不用安裝任何東西**。

## 2. 網路基礎

### 2.1 網址、網域、DNS
- **網域**：例如 `company.com.tw`。
- **主機名稱**：例如 `mailtemplates.company.com.tw`。
- **DNS**：電話簿，把主機名稱翻成主機的 IP 位址。IT 要在 DNS 加一筆紀錄，讓這個名字指到範本主機。

### 2.2 HTTP 和 HTTPS
- **HTTP**：網頁傳資料的方式，內容是明文，路上的人看得到。
- **HTTPS**：HTTP + 加密 + 憑證。資料加密，而且可以證明「這個網址真的是公司的」。

### 2.3 憑證（SSL/TLS 憑證）
- 像網站的身分證，由 **CA（憑證機構）** 簽發。
- 裝置要「信任」簽發的 CA，才不會跳警告或拒絕連線。
- **公開憑證**：由公開 CA 簽（例如 DigiCert、Let's Encrypt），所有裝置（含 Mac、手機）預設都信任。最省事。
- **公司內部 CA**：公司自己簽。網域內的 Windows 通常信任，但 Mac 或其他裝置要另外裝信任設定。
- 憑證會 **到期**（常見 1 年左右），要記得續期。

### 2.4 內網 vs 對外（Internet）
- 面板網頁是在 **同事自己的 Outlook** 裡打開的，所以只要同事的裝置連得到主機就行。
- **只在公司內網／VPN 用**：主機放內網即可，不必對外開放。
- **在家、外面不連 VPN 也要用**：主機要能從 Internet 連到。
- 範本主機自己要能 **往外** 連到 Microsoft 登入服務和 SharePoint（出站連線），這和「讓外面連進來」是兩回事。

### 2.5 Port（埠號）
- 一台主機可以同時跑很多服務，用 port 區分。
- HTTPS 預設是 **443**。範本服務在主機內部預設用 **8080**。

## 3. 主機端：Node.js 範本服務

### 3.1 Node.js 是什麼
- 讓 JavaScript 可以在主機上執行的「執行環境」，像 Java 要裝 JRE 一樣。
- 本專案需要 **Node.js 22.12 以上**，**只裝在範本主機上**，同事電腦不用裝。

### 3.2 範本服務做哪些事
| 網址 | 作用 |
|---|---|
| `/taskpane.html` 等 | 提供面板網頁本身 |
| `/api/config` | 告訴面板「公司的登入設定」（租戶 ID、App ID，都是公開識別碼） |
| `/api/catalog` | 已登入的同事拿「已發布」的範本 |
| `/api/admin/...` | 範本管理者：草稿、發布、撤回、還原歷史版本 |
| `/healthz` | 健康檢查，讓 IT 確認服務活著 |

服務收到請求時會 **檢查登入通行證和角色**，沒權限就拒絕。

### 3.3 `.env` 設定檔
- 放主機設定：公開網址、Entra 的各種 ID、SharePoint 位置、憑證檔路徑。
- 本身沒有密碼，但仍不可放到公開網頁目錄裡。

### 3.4 開機自動啟動
- Windows 主機：註冊成 Windows 服務（例如用 NSSM 等工具）。
- Linux 主機：用 systemd。
- 目的：主機重開機後，服務自己起來。

## 4. HTTPS 入口：反向代理 vs Azure

Node 範本服務 **只會講 HTTP**，所以前面一定要有東西處理 HTTPS。

### 4.1 比喻
- **Node 範本服務 = 廚房**：真正做事，但不處理加密。
- **反向代理 = 門口櫃台**：負責驗憑證、解密，再把請求在主機內部轉給廚房。

### 4.2 反向代理：IIS 或 nginx
- **IIS**：Windows Server 內建的網站伺服器，搭配 URL Rewrite + ARR 模組當反向代理。
- **nginx**：Linux 上最常用的網站伺服器／反向代理。
- 兩者做的事一樣，主機是什麼作業系統就用哪個。
- 憑證裝在 **反向代理** 上。
- Node 只聽 `127.0.0.1:8080`（只有主機自己連得到），外面碰不到它。

```
同事 Outlook ──HTTPS:443──▶ IIS / nginx（裝憑證）──HTTP:8080，只在主機內──▶ Node 範本服務
```

### 4.3 Azure App Service
- 微軟代管的主機服務：主機、HTTPS、憑證都由微軟處理。
- IT 只要把程式放上去，不用自己顧作業系統、不用架 IIS 或 nginx。
- 代價：要付 Azure 費用；預設對 Internet 開放，要限制內網要另外設定。
- 設定差異：`.env` 裡 `HOST=0.0.0.0`（讓平台的入口連得到）。

```
同事 Outlook ──HTTPS──▶ Azure App Service（微軟處理 HTTPS）──▶ Node 範本服務
```

### 4.4 Azure Static Web Apps（只放網頁時用）
- 專門放「純網頁」的服務，有免費方案，自動 HTTPS。
- 不能跑 Node 範本服務；適合「不需要集中範本 API」的簡化版。

### 4.5 `127.0.0.1` 和 `0.0.0.0`
- `127.0.0.1`：只接受「主機自己」的連線 → 搭配反向代理用。
- `0.0.0.0`：接受任何網路介面的連線 → 雲端平台或容器用。

## 5. 身分與權限：Microsoft Entra ID

### 5.1 Entra ID 是什麼
- 微軟的帳號與登入系統（以前叫 Azure AD）。公司 M365 帳號就是 Entra 帳號。
- **App 註冊（App registration）**：要讓某個程式用公司帳號登入，就要在 Entra 幫它「登記戶口」。

### 5.2 本專案的 3 個 App

| App | 角色 | 比喻 |
|---|---|---|
| **登入 SPA**（SendModes Outlook Client） | 面板網頁用它讓同事登入 | 發通行證的櫃台 |
| **範本 API**（SendModes Templates API） | 代表「範本服務」，定義權限和角色 | 通行證上寫的「可進入哪棟樓」 |
| **SharePoint 後端**（SendModes SharePoint Backend） | 主機自己去讀寫 SharePoint 用 | 主機的員工識別證 |

### 5.3 通行證（Access Token / JWT）
- 同事登入後，Entra 發一張 **有時效的數位通行證**。
- 面板拿著它向範本服務要範本；服務會檢查：
  - 是不是公司租戶發的
  - 是不是發給「範本 API」的
  - 是不是從「登入 SPA」來的
  - 有沒有 `Templates.Read` 權限、是什麼角色
- 通行證只放在面板記憶體裡，不存到瀏覽器儲存空間或網址。

### 5.4 Scope 和 Role
- **Scope（範圍）`Templates.Read`**：「這個 App 可以代表使用者讀範本」。
- **Role（角色）**：
  - **Reader**：可以讀已發布範本（一般同事）
  - **Editor**：可以編輯草稿
  - **Publisher**：可以發布、撤回
- **管理員同意（Admin consent）**：管理員事先替全公司同意，同事登入時就不會跳授權畫面。
- **指派必要（Assignment required）**：只有被指派的人（試行名單）才能登入這個 App。

### 5.5 為什麼不需要 Client Secret
- **SPA + PKCE**：網頁型 App 用 PKCE 流程登入，本來就不能也不需要藏密碼。
- **SharePoint 後端** 用 **憑證** 而不是密碼（見下一節），更安全、不會被複製貼上外流。

## 6. 範本庫：SharePoint

### 6.1 存什麼
- 一個檔案 `catalog-state.json`，裡面有所有範本的草稿、已發布版本、歷史版本。
- 放在一個 **不公開的專用網站**，只有 IT 管理者是成員。同事不直接存取，都經過範本服務。

### 6.2 Sites.Selected：只給一個網站的權限
- 一般的 SharePoint 權限可以碰全公司所有網站，風險太大。
- **Sites.Selected** 預設什麼都不能碰，管理員再 **單獨授權某一個網站**。
- 所以這個 App 只能讀寫那一個專用網站。

### 6.3 憑證驗證（公鑰／私鑰）
- 主機產生一對鑰匙：
  - **私鑰**：只放主機，不外傳，等於簽名用的印章。
  - **公鑰（憑證）**：上傳到 Entra 的 App，讓 Entra 可以驗證「這個印章是真的」。
- 主機用私鑰向 Entra 證明身分，換到 SharePoint 的存取權杖。
- 憑證有期限（本專案設 2 年），到期前要換新。

### 6.4 防止互相覆蓋（ETag）
- 每次讀檔都會拿到一個版本標記（ETag）。
- 寫回時帶上這個標記；如果中間有別人改過，SharePoint 會拒絕，面板顯示「內容已被其他人更新」。

### 6.5 失敗就停（Fail closed）
- 主機啟動時找不到範本檔，就直接停止，不會用錯的資料硬跑。
- 插入範本時找不到安全的位置，也會停止，不會亂蓋掉信件內容。

## 7. 一次完整的使用流程

1. **管理員** 在 M365 管理中心分配 XML → 同事的 Outlook 出現「寄信模式」按鈕。
2. **同事** 撰寫郵件 → 按按鈕 → Outlook 開啟 `https://公司網址/taskpane.html`。
3. 面板向 `/api/config` 取得登入設定。
4. 面板跳出登入視窗（`auth.html`）→ 同事用公司帳號登入 → 拿到通行證。
5. 面板帶通行證呼叫 `/api/catalog`。
6. 範本服務驗證通行證 → 用憑證換權杖 → 從 SharePoint 讀 `catalog-state.json` → 只回傳已發布、而且這個人看得到的範本。
7. 同事選範本、填欄位、預覽 → 插入 **目前草稿**（保留簽名與回覆歷史）。
8. 同事自己檢查後按傳送。**增益集從不自動寄信。**

範本管理者流程：同樣在面板的管理頁編輯草稿 → 發布 → 服務檢查是否有 Publisher 角色 → 寫回 SharePoint。

## 8. 安全設計重點

- 不申請讀信、寄信的權限；只操作目前這封草稿。
- 同事填的欄位內容和信件草稿 **不會上傳** 到範本服務。
- 個人偏好（例如常用設定）存在自己電腦的瀏覽器空間，和公司範本分開。
- 密碼、私鑰只在主機上，不放進資料包、不放進網頁目錄。
- 權限檢查在 **伺服器端** 做，不能靠改網頁繞過。

## 9. 部署方案比較

| 方案 | 要架什麼 | 優點 | 缺點 |
|---|---|---|---|
| **A. 完整版 + 公司主機** | 主機 + Node + IIS/nginx + 憑證 + 3 個 Entra App + SharePoint | 集中管理、權限、歷史版本；可只放內網 | IT 工作量最大 |
| **B. 完整版 + Azure App Service** | Azure App Service + 3 個 Entra App + SharePoint | 不用顧主機與反向代理 | Azure 費用；預設對外 |
| **C. 簡化版（只放網頁）** | 靜態網頁空間（如 Azure Static Web Apps）+ 上傳 XML | 最簡單，約半小時 | 無登入權限；改範本要 IT 換檔案 |
| **D. 現成產品**（如 Shared Email Templates） | 從整合式應用程式加入 | 廠商代管 | 訂閱費；範本存在廠商；功能不客製 |
| **E. Outlook 內建「我的範本」** | 不用部署 | 免費、零設定 | 只能個人用，不能統一發布 |
